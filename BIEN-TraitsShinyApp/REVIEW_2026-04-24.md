# BIEN-TraitsShinyApp Review

Date: 2026-04-24
Scope: product review, code review, and performance review of the deployed app at https://benquist.shinyapps.io/bien-traits-shinyapp/ and local sources.

## Central Goal

The app's central goal is to make BIEN trait data queryable, inspectable, and downloadable through an ecology-aware workflow that exposes data scope, provenance, and interpretation caveats before export.

Code evidence:
- `README.md` describes trait querying, visualization, provenance review, and reproducible query export.
- `app_gateway.R` implements a stepwise workflow: query, scope, trait selection, distributions, diagnostics, records, provenance, and download acknowledgement.

## Primary Use Cases

1. Retrieve BIEN trait observations for a single species, genus, family, or trait term.
2. Check how much data BIEN actually has for that query, including whether returned rows are truncated by the app limit.
3. Identify which traits are available and filter downloads to only the subset relevant to the analysis.
4. Explore rough trait distributions, missingness, unit heterogeneity, and source concentration before interpretation.
5. Export data together with a reproducibility manifest and BIEN R query script.
6. Preserve observation-level provenance fields, especially source citation and source URL, for downstream citation and QA.

## Problems The App Solves

1. It removes the need for users to write BIEN trait query code manually for common exploratory workflows.
2. It reduces the risk of silent over-interpretation by surfacing sample size, taxonomic breadth, truncation, missingness, and unit-mixing warnings.
3. It turns raw BIEN output into a more reproducible workflow by pairing downloads with query metadata and re-runnable R code.
4. It makes trait selection explicit, which helps users avoid exporting a large mixed bundle of traits when they only need a subset.

## Insights Users Can Gain

1. Which traits are well represented for a taxon or clade.
2. Whether observed trait coverage is broad across many species or concentrated in a narrow subset.
3. Whether the current query is likely to support only exploratory summaries versus more serious downstream analysis.
4. Whether a given trait query is dominated by a small number of studies or source datasets.
5. Whether data comparability is threatened by mixed units, low sample size, or high missingness.

## Under-Covered Or Missing Use Cases

1. Batch workflows are under-covered. The README promises CSV upload or pasted multi-species input, but the current gateway exposes a single target selectize control.
2. Spatial inspection is missing. The README promises map visualization, but the current workflow has no map tab or coordinate display.
3. Help and onboarding are under-covered. The README promises a help page with ecological caveats, but those caveats are distributed across the workflow rather than collected into a dedicated help surface.
4. Taxonomic reconciliation review is implied but not operationalized. The download acknowledgement asks users to confirm they reviewed reconciliation results, but the app does not expose a clear reconciliation-results step.
5. Trait-only scope expansion is under-explained. Partial trait matching can broaden one user-entered term into multiple exact BIEN traits, but the app does not present that expansion clearly before query execution.
6. Citation support is only partial. The manifest captures query metadata, but it is not itself a citation-ready source listing.

## Performance Findings

### High Priority

1. The query path performs two synchronous BIEN round-trips: one to fetch rows and one to compute exact total matches. This increases time-to-first-results and makes broad queries feel stalled.
2. The complete-records table renders the full result set into DT client mode, which is likely to become slow or browser-heavy for large queries.
3. The species-by-trait matrix builds a dense contingency table before trimming to the top species, which is unnecessarily expensive for high-cardinality queries.

### Medium Priority

1. Taxon suggestions preload large BIEN-backed choice lists on interactive paths, especially for species mode.
2. Trait catalog lookup is repeated in more than one place instead of being memoized once per process or session.
3. Expensive diagnostics are recomputed on trait-selection changes, even when the underlying query result has not changed.

## Correctness And UX Risks

1. README/app mismatch: deployed behavior does not match several documented features.
2. Mixed-unit distributions are still summarized and plotted as a single pooled numeric distribution, which can produce analytically invalid summaries.
3. Trait-only total-count messaging may be misleading when a partial term expands to multiple exact BIEN trait names but the count path still reflects the original token.
4. Provenance messaging is partly misleading: the acknowledgement text points users to a provenance manifest for citation, but the manifest is query metadata rather than a full citation artifact.
5. Timestamps are labeled as UTC without explicit timezone conversion.

## Recommendations

### Product And Use-Case Priorities

1. Decide whether this app is primarily a single-query trait gateway or a fuller trait workbench. Then align the README and UI to the same contract.
2. If the intended scope is broader, add the missing high-value workflows first: multi-species batch input, map view, and a dedicated help/caveats page.
3. Add an explicit reconciliation or query-resolution panel so users can see exactly what taxon/trait scope the app is using.
4. Add a small insights panel after each query that summarizes top-covered traits, source concentration, unit heterogeneity, and truncation risk.

### Speed Optimization Priorities

1. Move the complete-records DT to server-side processing.
2. Decouple total-match counting from the critical path so rows appear before exact BIEN totals finish computing.
3. Replace dense species-by-trait matrix construction with grouped counts followed by a compact pivot for top species only.
4. Reduce suggestion payload sizes and use stronger debounce/minimum-typing rules for BIEN-backed suggestions.
5. Memoize `BIEN_trait_list()` results so trait suggestion and trait expansion do not repeatedly hit BIEN.
6. Separate expensive diagnostics from trait-selection-only reactives so they do not recompute unnecessarily.

### Expected Impact

1. Server-side DT plus deferred count loading should materially improve perceived responsiveness on moderate and large queries.
2. Sparse matrix construction should reduce CPU and memory pressure for broad genus/family searches.
3. Suggestion caching and debouncing should improve first-interaction responsiveness, especially on hosted deployments.
